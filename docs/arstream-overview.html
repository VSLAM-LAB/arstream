ARStream pipeline

How the iPhone app captures camera frames and poses with ARKit, how they travel to the Mac over USB or Wi-Fi, and what the Mac does with them.

The big picture

The phone runs a small app that acts as a server: it tracks its own motion with ARKit and pushes every camera frame out on TCP port 5555. The Mac is the client: it connects to that port, either through the USB cable or over Wi-Fi, and receives a stream of frames, each with its image, camera intrinsics, pose and timestamp.

What runs on the phone

A single-screen SwiftUI app in ios/ARStream/. You install it once with pixi run ios-install (or ⌘R in Xcode) and then just open it.

FileWhat it does
ARStreamApp.swiftApp entry point; shows the main screen.
ContentView.swiftStarts the ARKit session (gravity-aligned world, autofocus off by default). Shows the camera preview, connection status, Wi-Fi address, fps, bandwidth and tracking state. Lets you pick resolution (1920×1440, 960×720, 640×480), max fps (10/30/60) and autofocus.
FrameStreamer.swiftReceives every ARKit frame. If a client is connected and the previous frame has finished sending, it downsizes the image, JPEG-encodes it on the GPU, rescales the intrinsics to match, and packs everything into one message. Frames that arrive while one is still in flight are dropped, so latency stays low on a slow link.
StreamServer.swiftTCP server on port 5555 using Apple's Network framework. Accepts one client at a time (a new client replaces the old one). Advertises itself on Wi-Fi as _arstream._tcp via Bonjour.
Info.plist + projectPermissions: camera, local network, Bonjour service name. Keeps the screen awake.

Where the pose comes from: ARKit's visual-inertial odometry, which fuses the rear camera with the phone's IMU. It works on any recent iPhone without LiDAR. ARKit runs at 60 Hz; the app sends at the chosen max fps.

What runs on the Mac

A Python package in python/arstream/, installed into the pixi environment. Dependencies: numpy, OpenCV (JPEG decoding), rerun (3D viewer) and zeroconf (Bonjour).

FileWhat it does
usbmux.pyTalks to usbmuxd, the system service macOS already uses to talk to iPhones over USB. Asks it to open a TCP connection to port 5555 on the phone. No extra tools (iproxy, libimobiledevice) needed.
discovery.pyFor Wi-Fi: browses Bonjour for _arstream._tcp and returns the phone's IP. Only looks on the Mac's Wi-Fi/LAN interface, so a plugged-in cable doesn't confuse it.
client.pyARStreamClient: reads messages off the socket and turns each into a Frame. Converts the pose from ARKit's camera axes to OpenCV's.
recorder.pyWrites frames to disk in a TUM-RGB-D-style layout (see below).
cli.pyThe arstream view and arstream record commands.

One frame's journey

  1. phone ARKit produces a frame

    A 1920×1440 camera image plus the camera's pose in the world, its intrinsics and a timestamp, all from the same instant.

  2. phone Encode

    Resized (default 960×720) and JPEG-encoded at quality 0.8, about 60 kB. Intrinsics are rescaled to the new size.

  3. phone Package

    A JSON header with the metadata is put in front of the JPEG, with a small fixed-size prefix that says how long each part is.

  4. link Send

    Written to the TCP connection. Over USB, usbmuxd carries it through the cable; over Wi-Fi it goes through the router.

  5. Mac Receive and parse

    client.py reads the prefix, then exactly that many header and JPEG bytes, and builds a Frame. The JPEG is only decoded when you access frame.image.

  6. Mac Use

    The viewer draws it in rerun, the recorder writes it to disk, or your code feeds it to SLAM.

Communication protocols

There are three layers. The bottom one depends on the connection type; the top one is the same for both.

USB usbmuxd tunnel

macOS's usbmuxd listens on the local socket /var/run/usbmuxd. The Mac sends it a small "Connect to device X, port 5555" request (a binary header plus an XML plist). After it replies OK, the same socket becomes a plain pipe to the phone's TCP server, carried over the cable.

Wi-Fi Bonjour + TCP

The phone announces _arstream._tcp using Bonjour (multicast DNS), the same mechanism AirPrint and AirPlay use. The Mac asks "who offers this service?" and gets the phone's IP and port, then opens a normal TCP connection. Both devices must be on the same network.

The ARStream message (same for USB and Wi-Fi)

Each frame is one message. The phone only sends; the Mac never writes anything back. Integers are little-endian.

The magic bytes let the Mac detect if it ever loses its place in the stream. The JSON header looks like this:

{
  "seq": 1234,                      // frame counter
  "timestamp": 99638.308,           // seconds since phone boot (same clock as the IMU)
  "width": 960, "height": 720,      // size of the JPEG
  "K": [722.4, 0, 481.5,            // 3×3 intrinsics for this JPEG, row-major
        0, 722.4, 358.9,
        0, 0, 1],
  "T_world_camera": [ … 16 … ],     // 4×4 camera-to-world pose, row-major, ARKit axes
  "tracking": "normal",             // or limited_initializing, limited_excessive_motion, …
  "exposure_duration": 0.01         // seconds
}

Coordinate conventions

ARKit and OpenCV disagree on which way a camera looks. The phone sends ARKit's raw pose; client.py converts it to the OpenCV convention most SLAM code expects by flipping the camera's y and z axes.

World frame

ARKit's: gravity-aligned, y points up, origin where the app started tracking. Units are metres.

Camera (ARKit)

x right, y up, z backward (out of the screen towards you). Kept in frame.header.

Camera (OpenCV)

x right, y down, z forward. This is frame.T_world_camera.

Using it from your own Python code

from arstream import ARStreamClient

with ARStreamClient.usb() as client:          # or ARStreamClient.tcp("192.168.1.102")
    for frame in client:
        frame.image            # BGR uint8 numpy array (H×W×3)
        frame.K                # 3×3 intrinsics for frame.image
        frame.T_world_camera   # 4×4 camera-to-world, OpenCV camera axes
        frame.timestamp        # seconds, phone clock
        frame.tracking         # "normal" when ARKit's pose is reliable

What a recording contains

recordings/20261009_103000/
├── rgb/99638.308000.jpg …   original JPEGs from the phone, named by timestamp (not re-encoded)
├── rgb.txt                  timestamp → image file, TUM format
├── arkit_poses.txt          timestamp tx ty tz qx qy qz qw, TUM trajectory format
└── frames.jsonl             one line per frame with the full header (intrinsics, tracking, …)

The TUM format means most SLAM tools and evaluation scripts (for example evo) can read it directly. ARKit's poses serve as a reference trajectory to compare your VSLAM against.

Limits and next steps

  • No depth yet. The iPhone 15 has no LiDAR. A LiDAR iPhone would add a depth map to the same message.
  • Bluetooth is not an option. iOS apps only get Bluetooth Low Energy, far below the ~15 Mbit/s the stream needs.
  • Campus Wi-Fi (eduroam) usually blocks device-to-device traffic. Use the phone's Personal Hotspot instead.
  • Free Apple ID signing expires after 7 days; re-run pixi run ios-install.
  • Possible next steps: a C++ client with the same API, raw IMU data in the stream, and running a VSLAM such as ORB-SLAM3 against ARKit's poses.
